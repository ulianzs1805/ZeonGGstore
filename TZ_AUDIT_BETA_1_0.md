# ZeonGGStore Beta 1.0 — аудит ТЗ

Этот файл фиксирует прогресс по исходному ТЗ, чтобы разработка не ходила по кругу.

Статусы:
- DONE — проверено и реализовано.
- PARTIAL — есть часть реализации, требуется отдельная проверка/доработка.
- MISSING — по текущему поиску реализации не найдено.
- VERIFY — требует ручной или серверной проверки перед Beta.

## 1. Блоки, которые уже активно дорабатывались

### Кейсы и дроп
- PARTIAL — кейсы, открытие, отображение дропа и процентов уже дорабатывались.
- VERIFY — серверная выдача, защита от повторных запросов и атомарность результата.
- PARTIAL — StatTrack требует отдельной проверки после появления корректных PNG-ассетов.

### Авторизация и профиль
- PARTIAL — Google OAuth исправлялся и вход работает по последней проверке.
- VERIFY — регресс после следующих деплоев.

### Промокоды
- PARTIAL — создание и активация проверялись.
- VERIFY — журналирование, защита от повторной активации и лимиты.

### Админка
- PARTIAL — Z-Coin, роли, Dev Console и цены уже дорабатывались.
- TODO — не продолжать косметику без отдельного пункта ТЗ.

## 2. Критические незакрытые пункты ТЗ

### Апгрейдер — MISSING/VERIFY
Проверить отдельно:
- серверный расчёт шанса;
- минимум 0.1%;
- множители и целевые предметы;
- блокировку предметов на время операции;
- защиту от повторного запроса;
- уникальный ID операции;
- запись результата в журнал.

### Контракты — MISSING/VERIFY
Проверить отдельно:
- серверный результат;
- правила выбора предметов;
- защиту инвентаря;
- блокировку предметов;
- атомарность операции;
- уникальный ID;
- журналирование.

### Башня — MISSING/VERIFY
Проверить отдельно:
- лёгкий режим: 4 этажа;
- средний режим: 8 этажей;
- сложный режим: 16 этажей;
- мины выбираются только там, где это предусмотрено ТЗ;
- коэффициенты;
- частичный проигрыш;
- кешаут в любой момент;
- серверная обработка результата.

### Тестовый дроп — MISSING
Нужен отдельный безопасный режим:
- выбрать Test User;
- выбрать Case;
- выбрать Test Item;
- показать сценарий выдачи;
- не менять реальный баланс;
- не выдавать реальный предмет;
- не использовать скрытую персональную подкрутку для реальных игроков.

### Аварийное отключение режимов — MISSING
В админке нужны независимые переключатели:
- Cases ON/OFF;
- Upgrade ON/OFF;
- Contracts ON/OFF;
- Tower ON/OFF;
- Deposit ON/OFF.

Выключение одного режима не должно останавливать остальные части сайта.

### Maintenance Mode — MISSING
Нужен глобальный режим:
- пользователи видят сообщение о техническом обслуживании;
- администратор сохраняет доступ к админке.

### Backup и восстановление — MISSING/VERIFY
Нужно определить и проверить:
- резервные копии базы;
- конфигурации;
- важные файлы;
- пользователей;
- балансы;
- инвентари;
- транзакции;
- конфигурации кейсов;
- реальный сценарий восстановления.

### Критические операции и журнал — PARTIAL
Для изменения баланса, вероятностей, удаления предметов и массового изменения цен требуется:
- дополнительное подтверждение;
- серверная проверка;
- уникальный ID операции;
- запись в журнал.

## 3. Архитектурные правила Beta 1.0

Все важные решения должны проходить:

Пользователь -> интерфейс -> Backend -> проверка -> игровая логика -> Database -> результат -> интерфейс.

Клиент не является источником истины для:
- Z-Coin;
- игровых результатов;
- инвентаря;
- вероятностей;
- критических административных операций.

## 4. Следующий порядок работы

1. Аварийное отключение игровых режимов + Maintenance Mode.
2. Тестовый дроп без изменения реальных данных.
3. Полный аудит Апгрейдера.
4. Полный аудит Контрактов.
5. Полный аудит Башни.
6. Проверка защиты инвентаря и игровых операций.
7. Backup и сценарий восстановления.
8. Финальный Beta-аудит и тестирование.

Важно: после закрытия каждого блока обновлять этот файл, а не переходить к случайной косметике уже существующих панелей.
